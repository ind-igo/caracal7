Implementation decisions that the spec does not settle. Dated, newest last.

- 2026-09-04: Tile op per backend. - 2026-09-04: Tower constants for e = 16 (`field.mojo`): i^2 = -1, j^2 = 2 + i, u^2 = j, y^2 = u. Each is a non-square in the field below (2 + i has norm 5, a non-residue mod 127; j and u follow from the (q-1)/4 argument); tests check C1..C3 by exponentiation. Elements are byte lanes `SIMD[uint8, 2^k]`, low half on 1, high half on the generator, so F4 acts coordinate-wise on E. Reductions use unsigned `min(x, x - 127)` instead of a select, because scalar comparisons return `Bool` in Mojo 1.0.
- 2026-09-04: `Params` is a trivially-register-passable struct passed as a comptime value; `REFERENCE` is the milestone-1 profile (72 × 32, L0 = 80,640, 105 queries at rate 1/140).
- 2026-09-04: `gemm.mojo`, byte GEMM mod 127 on the M1 Pro at 1024^3: naive 170 GMAC/s; threadgroup + register tiling (64/64/16, 4 x 4 per thread) 296 GMAC/s; BK = 8 gives 307. Register tiles must be `SIMD[int32, TM*TN]` locals with a runtime k loop: a `TileTensor` stack allocation with a fully unrolled k loop ran 3x slower than naive. A 128 x 128 block with 8 x 8 register tiles crashes the Metal compiler (XPC_ERROR_CONNECTION_INTERRUPTED at pipeline creation); tile sweeps stay at or below 4 x 4 per thread on this GPU until that is understood.

## GEMM rung 5: vector loads, per-row accumulators (2026-09-04)

`gemm127_vec` loads 4 bytes per thread per read from global memory, stores the A tile transposed in
shared memory so the register loads are 4-byte vectors too, and keeps the accumulator as TM separate
`SIMD[int32, TN]` rows. The single `SIMD[int32, TM*TN]` accumulator was the Metal compiler crash
(XPC_ERROR_CONNECTION_INTERRUPTED): with per-row vectors 4x8 and 8x8 register tiles compile.

Measured at 1024^3 on M1 Pro: naive 174, tiled 4x4 339, vec 4x4 360, vec 4x8 220, vec 8x8 157 GMAC/s.
Larger register tiles lose occupancy on this GPU, so the M1 backend keeps 64/64/16 with 4x4 and the
vec kernel. BK=32 also collapses (145). The next rungs on the ladder (double buffering, warp tiling)
wait until the encoder shows where the time goes.

## Encoder rung 1, arena, tables (2026-09-04)

**Arena.** `arena.mojo`: one `DeviceBuffer[uint8]` per prover instance, offsets from a bump planner
(`Bump`, 256-byte aligned). Kernels take the base pointer plus `Int64` offsets and `Int32` counts:
Mojo's `enqueue_function` refuses `Int` and user structs without a private `DevicePassable`
conformance, so offsets are plain fixed-width integers. Tables live in the arena too, uploaded once.

**Domains** (`tables.mojo`). `gamma2` = the first `(lo, hi)` in F2 with full order 16128;
`omega_l = gamma2^(16128 / h_l)`; `rho_l = omega_l^(2^a_l)` (checked to lie in F). The order-L0
subgroup of F4* is generated by `g = c^((127^4 - 1) / L0)` for the first `c = (lo, 0, hi, 1)`
whose `g` has exact order L0. Leaf `s` of the level-1 code is the point `g^s`. Tables: inverse-DFT
matrices per axis in F2 (dense, `h_l^2` entries), `rho_l` powers, `gA` powers, and the three
Good-Thomas DFT matrices in F4.

**Packing basis.** `pack` uses the coordinate basis `(1, i, j, ij)` of F4 over F, so a packed
symbol is the four slot bytes verbatim. The spec's `b = (1, j', j'^2, j'^3)` is a different basis
of the same space; the verifier's `g_{s,tau}` uses the coordinate basis.

**RS encode structure.** `L0 = 2^b * 315` is split Good-Thomas across the coprime parts, and 315
again as 5 x 7 x 9; no twiddles between stages. Because the message has `K = N/4` symbols and
`K / 315 <= 2` at the reference profile, the 2^b-point transform is done as a direct sum over the
two or three nonzero inputs per line (pass A). Then three in-place radix stages; the last one
scatters into the leaf-major `code`. ponytail: pass A is O(L0 * K / 315); at proxy sizes it becomes
a Cooley-Tukey stage list on the 2^b part.

**Measured, 64 columns, M1 Pro (rung 1, one thread per output).** trace -> packed 0.98 ms
(15 us/column). rs_encode 29 ms (457 us/column, 65 GMAC/s): pass A 6.9, stage 5 4.6, stage 7 6.1,
stage 9 12.0 ms. Every pass moves bytes at 3-4 GB/s against a ~200 GB/s roofline: consecutive
threads read 4-byte symbols 252 bytes apart in stage 5, and the scatter write is random. The next
rung is coalescing (ladder step 2): transpose the digit order per stage so a SIMD group reads
contiguous lines, and stage the scatter through threadgroup memory.

**Rungs 2-3 on rs_encode (2026-09-04).** Three changes, measured at 64 columns: (1) `f4_mac_wide`,
signed int32 coordinate accumulation with one reduction per output (29 -> 13.9 ms); (2) column-fastest
layouts for `packed`, `etmp`, `code`, a SIMD group handles 32 consecutive columns for one (row, t1), so
every load and store is contiguous and twiddles are broadcasts (13.9 -> 11.5 ms); (3) a 2D launch
(block 32 x 8) and two 315-entry index tables `crt`, `ruri` replacing all runtime integer divisions
(11.5 -> 4.7 ms; pass A alone 4.8 -> 1.0 ms). Now 74 us/column, 401 GMAC/s, above the GEMM's
360 because the twiddle operand is a broadcast. Stage 9 with the scatter is 2.0 of the 4.7 ms.
Integer division is the hidden cost on this GPU: prefer tables and shifts in every index computation.

## Skeleton before kernels (2026-09-04)

Indigo asked whether to scaffold the prover and fill it in, or keep going bottom-up. Decision: a
thin host skeleton, no stubbed kernels. `prover.mojo` plans the arena for every buffer of design
section 3 and enqueues every stage of spec section 10 in order; `proof.mojo` fixes the shape and
byte layout; `verifier.mojo` lists the seven steps; the stage modules carry real signatures. Each
missing stage raises `not implemented: <name>` where it would run, so `prove` stops at the first
missing stage (`transcript.absorb` today) and never fakes an output. Kernels replace one raise each.

The hash is a comptime parameter `H: Hash` (`hash.mojo`) on merkle, transcript, prover and
verifier, at Indigo's request, so the tree and transcript hash can change without touching kernels.

Arena for the reference profile with 53 + 48 columns: 76 MiB, dominated by the two codeword
buffers and their RS intermediates (4 x 80640 x 4 bytes per column).

## Blake3 and the transcript (first raise filled)

- `hash.mojo` is standard Blake3 (hash mode, keyed mode, tree mode up to 4 MiB per message), verified against the official vectors at 0, 1, 63, 64, 65, 1024, 1025, 2048, 2049, 3072 bytes and one keyed vector. Merkle leaves and nodes are plain Blake3 of the row or of `left || right`, so any Blake3 tool can recompute a root.
- Transcript composition: `state <- blake3_keyed(key=state, ds || message)`; challenge block `t` is `blake3_keyed(key=state, LE64(t))`. F elements are rejection-sampled bytes below 127, positions rejection-sampled u32 below `L`. The counter resets on every absorb. `sample` is one function that runs in the one-thread kernel and in `HostTranscript`, so the verifier mirror cannot drift.
- The absorb kernel is one thread and reads bytes one at a time. ponytail: large absorbs (openings, clear vector) can Merkle-reduce in parallel and absorb the root; do it when the transcript shows up in the profile.

## Merkle tree and multiproof

- Levels have ceil(n/2) nodes; an odd last node is copied up unchanged. L0 = 2^b * 315 is never a power of two, and padding to one would double the leaf hashing for nothing. The verifier knows every level size, so the copy rule is unambiguous.
- Tree layout (node, DIGEST), level 0 first, root last. One launch per level, thread per node.
- Multiproof: `[u32 bytes][rows at the sorted distinct positions][sibling frontier]`, the frontier walked level by level in ascending order, each sibling once. One thread walks the frontier (positions stay in registers, at most 1024 queries), then a thread block per row copies the opened rows. The exact byte count lives on the device; the host reads back the bound and trims by the header, so no challenge ever reaches the host.
- `check_multiproof` in merkle.mojo is the verifier side, written next to the kernel that produces the bytes.
- Measured: 80640 leaves x 404 B in 6.7 ms (4.9 GB/s) on the M1, byte-at-a-time loads. ponytail: word loads in `_hash` when the tree shows up next to the encoder in the profile.

## Audit fixes (skeleton orchestration)

Two independent reviews of everything through the Merkle commit found the kernels and math sound and the host skeleton wrong in the ways a skeleton is: one challenge buffer overwritten before its readers ran, `positions` never written, one multiproof region reused without a read-back, the Q tree encoded from an unfilled `packed`, the transcript state never zeroed, no `alpha`, and a prefix that hashed twiddle tables instead of the parameters and public inputs. Fixed as follows.

- **One arena region per challenge** (`stage1`, `z`, `beta_gamma`, `positions`, `batch`, `r`), sized from `Shape`; every squeeze names its destination. Nothing is reused within a proof.
- **Proof values are staged, not read back.** `ProofWriter.stage` enqueues an async copy out of the arena in stream order; `finish` synchronizes once and assembles. A multiproof region can be reused because the copy is queued before the next gather. `fixed_bytes` mirrors the writer exactly.
- **Transcript prefix** is `prefix_bytes`: version, every `Params` field, derived query count and `n_cw`, the shape, the tail schedule per level, and the public inputs. Prover and verifier build the same bytes; the state is zeroed at the start of every proof.
- **Milestone 1 has no Z tree**, so `alpha` is the fourth stage-1 challenge. When the Z tree lands, it moves back behind its own barrier.
- **Tail schedule** tracks the remaining binary digits (the odd digit is never folded), uses `tail_digits`, and chooses the smallest domain `m * d` (`d | 161280`, `m` in {1, 2, 4}) at rate <= 1/32, or the largest domain (645120) if that still gives rate <= 1/16. This is spec 9.5's rate rule ("the largest L the time budget allows, 1/16 to 1/32") made computable; the tail levels are small next to level 1, so the larger domain costs little and every query saved cuts bytes and verifier work at every level. The spec's worked row was updated to the rule's numbers.
- `e` must be 16 (`field.mojo` fixes E). Blake3 chunk stack 24 deep (16 GiB). The GEMM lazy-reduction cadence asserts `BK | 128`.
- Not done: the rate-driven `n_cw` split (milestone 2 with the proxy grid), and the `<w_z, stored(c)> = c(z)` test, which is the first test of the open stage.

## Backend materialized, residual stage on the GEMM skeleton (2026-09-04)

Before the residual stage, the `Backend` / `tile_mac` rule of design section 9 was prose. Indigo agreed to make it code first and write the residual on it, so the third GEMM-shaped stage is the first one that has to satisfy the rule.

- `backend.mojo`: `Backend` carries only the fields a kernel reads (threadgroup bytes, `mma_k`, `max_terms`, `vec_bytes`, default tile); `BACKEND = SIMD_LANES` is the one value. `tile_mac[B, TM, TN, neg]` is the rank-1 register-tile update (`mma_k = 1`); `gemm.mojo`'s tiled and vec kernels now call it, so the standalone GEMM and the skeleton share the hot op. An MMA backend replaces `tile_mac`, the `Backend` value, and the skeleton's fragment loads and k step (it consumes `mma_k` tile columns per call); the stages above the skeleton do not change.
- `gemm_f2` is the shared skeleton: F2 operands as two byte planes in shared memory, four `tile_mac` per k for the complex product, signed int32 lanes reduced every `max_terms = 128` (2 * 126^2 per term stays under `WIDE_BIAS`). Every dimension is predicated, so M, N, K are free and only the tile has to be legal. Operands go through a `Loader`: `Strided` with a two-level n split (D = 8 turns an E-valued buffer into 8 F2 lanes), `Family` gathers the residual's B operand from the LDE on the fly. Kernel arguments can be structs: `Operands` conforms to `DevicePassable` with `encoder.encode(self, target)`.
- The residual stage is six skeleton launches plus two small kernels: LDE axis 1 and 2 (the twist lives in the `g_l^(j k)` tables, no separate pass), the family pass as `C[8 lanes, point] = kappa[8, entries] . X[entries, point]`, then `q1m` (Q1 on the coset straight from R over all of G1, `63` on the diagonal and `64 * s1ext` on the even points), `qinv1`, `ginv2` for the A, B coefficients, `q2m = 63 winv1`, `qinv2` for Q2, and the odd-digit DFT into plain `(x1, x2, r)` slots. `k_fold_alpha` computes `kappa = coef * alpha^family` on device after the challenge.
- Family entries are 32 bytes, one per (family, read); shifts are G offsets (`2k` for `omega^k`). The gate tables `g_l^j - e_l` sit next to the twiddles. `residual_at` in `residual.mojo` is the host evaluator the verifier's step 5 and the tests share. Six synthetic families over eight columns (linear, quadratic, both gates, a within-chain shift, a cyclic shift, an axis-2 shift) with a trace that satisfies them are the milestone-1 statement; the family table is hashed into the transcript prefix.
- Tests: the skeleton on ragged shapes and the lane view; LDE against direct evaluation; R = 0 on H and R matches a host walk of the table on G; the DEEP identity `R(z) = (A + z2^h2 B)(z1^h1 - 1) + Q2 (z2^h2 - 1)` at a random z in E^2 with `B`, `Q2` top coefficients zero; the plain slots. `prove` now runs through the Q tree and stops at `build_queries`.
- Measured (M1 Pro, 64 columns, 260 entries, G = 9216): lde 4.7 ms, residual 6.0 ms, quotient 1.7 ms. Base-MAC rates are 34, 13, and 30 GMAC/s against the encoder's 401: the skeleton is at rung 1 of its own ladder (scalar 2-byte loads, no vector loads, 72 blocks of 32 threads for the family pass at this small grid). ponytail: vector loads in the skeleton's load phase and split-K or BN = 32 for the family pass when the residual is next to the encoder in the profile; the dense O(h^2) LDE stays until mixed-radix stages (spec 10.2) are worth their tables.

## Open stage; quotient columns as values on H; review fixes (2026-09-04)

- **Quotient columns are ordinary columns.** Spec 9.2 stores `A`, `B`, `Q2` coordinate columns in plain `(x1, x2, r)` slots with their own query `Mon(x) L(r)`. But the fold `y = sum_c beta_c stored(c)` is one vector over both trees and the tail carries one query type, so two slot conventions cannot share a claim. Since all three have bidegree below `(h1, h2)`, each equals the interpolant of its values on `H`; so `quotient` now ends with forward DFTs to the values on `H` and writes the 48 coordinate columns as the quotient tree's trace, and the witness encoder (`idft2`, `to_stored`, `pack`, `rs_encode`) takes it from there. No plain-slot map exists anywhere: `open`, `fold`, the verifier and the tail see one slot layout. `Q(z) = sum_tau e_tau alpha_{(Q, tau), 0}` from the coordinate openings. Spec 9.2 now states this rule (edited 2026-09-04 after a Codex second opinion).
- **Opening points** (spec section 3, milestone 1): the DEEP point `z` and one point per distinct read shift of the family table, `(g1^dj1 z1, g2^dj2 z2)`, in first-seen order; every column is opened at every point. `residual.shift_points` derives them, `Shape` takes its `P` and entry count from the family table, the prover uploads the `(dj1, dj2)` list once.
- `open.mojo`: `k_build_queries` computes the twelve-piece weight of every `(point, slot)` from scratch (`Mon`, `Par`, `L(r)` with the Kronecker fallback, `i (Mon - Par)` on the `v` slots, `Mon` on the four fixed classes); `open` and `fold` are lane GEMMs on the skeleton with the F bytes read through the `Bytes` loader, the fold's second tree accumulating (`acc=True`). Verified: `<w_z, stored(c)> = c(z_p)` for every witness column and point against a host Horner evaluation, the quotient openings against their coefficient tables, and the fold against a host sum.
- **Milestone 1 proves end to end at the reference profile** (no committed tail level: `y_2` is the clear vector), 14,116 proof bytes for 8 + 48 columns and 4 points. The verifier runs steps 1, 2, 5 (the residual identity from the openings via `residual_at`) and stops at the tail; a flipped opening byte fails step 5.
- Review fixes (Codex, Opus): entry shifts are u16 (a byte truncated every grid with `h > 128`); a gated entry must be linear (`Families.add` raises: two columns and a gate exceed the degree bound and alias on `G`); the transcript prefix carries `H(family table)` instead of the table (the prefix is fixed size again, and the artifact hash of statement-layer 6 is what it should have been); the verifier checks the table against `shape.entries`; the `max_terms` bounds are comptime asserts in both GEMMs; the pre-skeleton wide MAC helpers are deleted; design rule 3 records the skeleton's runtime `M, N, K` and strides; the MMA claim is corrected (the skeleton's fragment loads and k step change with `mma_k`, the stages above do not).
- Toolchain: `F2(byte, 0)` inside a kernel crashes the Metal compiler ("failed to compile metallib"); build the vector and assign the lane instead.
- Not done: a second test profile with `m2 > 1` (`REFERENCE` has `m2 = 1`, so the axis-2 odd digit is exercised nowhere); split-K for `open` (one block per point over `N` slots); `ext_inv0` is the kernel inverse, `ext_inv` still raises on zero for the host.

## Verifier step 7, clear-vector case (2026-09-04)

- The reference-profile proof verifies end to end. Step 7 with no committed tail level: `y_2` from the clear, `S` from the transcript, both level-1 multiproofs through `check_multiproof`, consistency at every opened position, then the evaluation claim `<y, sum_p gamma_p w_{z_p}> = sum beta_c gamma_p alpha_{c,p}` directly. 123,632 proof bytes at 8 + 48 columns, 105 queries; the multiproofs are two thirds of it.
- **Consistency is the alphabet rule of 9.1 literally**: `encode_at` evaluates `Enc(y)(g^s)` in `E (x) F4` as four `E` coordinates (the `F4` power acts on the coordinates by its 4 x 4 matrix, never by a product inside `E`) and compares coordinate-wise with `sum_c beta_c X[s, c]` over both trees. test_open checks the rule against the device codewords and that it is not vacuous.
- `slot_weight` in open.mojo is the one definition of `w_z[slot]`; the kernel and the verifier call it (the rho tables are gone from the kernel: `f_pow` on the odd-digit generator is cheaper than the load). The verifier's evaluation claim is `O(P N)` slot weights on the host, ~0.3 s here. ponytail: the twelve-term tensor form of 9.1 when a verifier budget exists.
- A flipped byte in the clear vector fails at the multiproof parse, not at consistency: `S` moves with the transcript. Only a dishonest prover reaches the consistency check, so its non-vacuity lives in test_open rather than in a tamper test.

## Encoder on every schedule domain; the tail end to end (2026-09-05)

- **The RS encoder takes any schedule domain.** `RsDomain(L0, m)` is `m` cosets `gamma4^k D0` of the order-`L0` subgroup (leaf `s` is `gamma4^(s // L0) g^(s mod L0)`); `RsTables` holds one domain's twiddles, Good-Thomas maps and the coset twist `gamma4^(k i)`; `rs_encode_on` runs pass A with the twist and the radix stages of the odd part (`5`, `7`, `9` or `3`; `M | 315`) per coset. Message length is a runtime argument with a reduction every `F4_MAC_MAX` products (level 3 of the 288 x 128 grid has `K / M = 64`). `b` and `M` are runtime in the kernels; the stage stride is dispatched to a comptime value because a runtime division there cost a quarter of the encoder. Level 1 at the reference profile is unchanged at 5.8 ms; the old `L0 = 2^b * 315`, `m_cosets = 1` asserts are gone. Verified against direct evaluation at `4 x 4608` (`M = 9`) and `2 x 672` (`M = 21`).
- **Tail kernels are rung 1**, one thread per output: `k_points` (leaf points of the sampled positions), `k_expected_level1` (the `E (x) F4` encoding of `y_2` at a point, four `E` coordinates), `k_expected_tail` (`sum_row y[row] pt^row`, `E x F4` slice-wise), `k_materialize_level1` / `k_materialize_tail` (`w~ = batch_0 running + sum_q batch_q g_q`), `k_round_partial` + `k_round_sum` (round `d` binds digits below `d` to `r`, sums the rest; 1024 partial sums, one thread adds them), `k_fold8` (`Mat(x) r_bar` for the message and for the query). The level-2 running query `sum_p gamma_p w_{z_p}` is one more kernel. test_tail checks the identity the sumcheck rests on, `<y, w~> = batch_0 <y, running> + sum_q batch_q v_q`, the three round sums against the verifier's quadratic interpolation, and the fold, on device data against host formulas.
- **The verifier runs the whole tail on the host in the direct form**: per level, root, the previous level's multiproofs, `v` against the opened rows (alphabet rule at level 1, `<X[s, :], r_bar>` later), `w~` materialized as a vector, three sumcheck checks, the query folded by `r_bar`; then the clear vector's consistency and `<y_ell, w~_ell>`. ponytail: 3.3 s at 288 x 128 (a `(q, i)` power table and `O(|y_l|)` E-work per level); the tensor form of 9.3 when a verifier budget exists.
- **288 x 128 proves and verifies end to end**: two committed levels (4608 rows on 161280, 576 rows on `4 x 4608`), 576 elements in the clear, 200,376 proof bytes at 8 + 48 columns (multiproofs dominate: `4 * 56` bytes per level-1 row plus paths), prove 0.85 s on the M1 Pro including kernel compilation for the profile. A flipped byte in a sumcheck message fails the round check.
- Spec wording (Codex, 2026-09-04): 9.1 names the packing basis `(1, j', j'^2, j'^3)`; the code packs and checks in the tower coordinate basis `(1, i, j, ij)`. Any `F`-basis gives the same code; the spec sentence should name the coordinate basis. Not a vault edit without a go.
- Not done: the `n_cw > 1` split (comptime assert in the verifier, `n_cw() = 1` in Params); the materialize kernels compute `pt_q^i` by a pow per `(slot, q)`; `k_round_sum` is one thread over 1024 partials; the level-2 expected symbols are one thread per query over `N / 4` symbols.
- Review fix (Codex): a domain with odd part 1 (a pure power of two) has no scatter path in the encoder, so `Params.check` rejects such an `L0` and `tail_schedule` skips such divisors; before, they passed both and failed at the first encode.
- Review fixes (Opus): the proof docstring no longer lists a params digest (the parameters are bound through the transcript prefix) and says two multiproofs at level 1; `Shape.__init__` calls `Params.check`; a sampled position missing from the opened list raises instead of indexing row 0; the verifier checks `shape.clear_length` against the schedule before reading the clear vector; the RS tables are 4-byte aligned in the table span. Observation left as a spec question: `v` is redundant (the verifier recomputes every entry from the opened rows); dropping it saves ~7 KB at 288 x 128 and needs the opened rows absorbed instead.

## Open split-K; expected symbols from committed rows (2026-09-05)

- **`open` is split-K.** Block `(p, s)` reduces slots `[s K, (s + 1) K)` of point `p` into a `(P, splits, column, e)` partial region, one byte-sum kernel finishes mod 127. `splits` is the largest power of two `<= 64` dividing `N`. The skeleton gained one field, `sb_zd`: the B operand's batch index is `z % sb_zd`, since the stored columns depend on the chunk only while `w_z` and the partials depend on `(p, s)`. 288 x 128: 381 ms to 23 ms.
- **Expected symbols come from the committed rows, not from the message** (a review suggestion). The encoder is linear, so `Enc(y_2)(pt_s)` is `sum_c beta_c X[s, c]` coordinate-wise over both trees, and `Enc(fold(y))(pt_s)` is `sum_a r_bar[a] X[s, a]` over the 8 leaf symbols: the same expressions the verifier checks. One thread per `(q, tau)` over the columns replaces one thread per `q` over `N / 4` symbols; transcript and proof bytes are unchanged (sizes match byte for byte). 125 ms to under 1 ms at level 2. test_tail checks the tail form against the host encoder of the folded message (`Enc(y)` encoded on device, folded on device, evaluated on host) and the level-1 form as the row identity; the alphabet rule that makes the level-1 form correct is in test_open.
- 288 x 128 warm prove: 843 ms to 373 ms. The budget is now `encode Q` (74), `build_queries` (63), `quotient` (37), `encode W` (25), `open` (23): the encoders are the largest item again, as the design expects.

## Proof staging pool (2026-09-05)

- **`ProofWriter` stages into one host buffer allocated with the prover** (rule 6 applied to host staging, as design.md says). `proof_pool_bytes` sizes it from the shape: the fixed bytes at the largest prefix, every multiproof region bound, and the transcript-prefix upload region. Per proof: `reset`, host values written straight into the pool, device values as async copies into pool regions, the transcript prefix uploaded from a pool `scratch` region. No host buffer is created and no synchronize happens between the prefix and `finish`; before, every staged value created a host buffer and every host write synchronized. `finish` assembles with `memcpy` per segment (was a per-byte loop). finish 18 ms to 1 ms; warm prove 64 to 52 ms at 72 x 32, 349 to 326 ms at 288 x 128.

## One GEMM: gemm.mojo deleted, the skeleton tuned (2026-09-05)

- **`gemm.mojo` is gone.** It was the byte-GEMM ladder climb (naive, tiled, vec) that produced the 2026-09-04 numbers, used only by its test and bench; the skeleton `backend.gemm_f2` is the one GEMM (design section 8). `bench/bench_gemm.mojo` now runs the skeleton at 1024^3 on plain strided F2 operands, so tile numbers measured there are the numbers every GEMM-shaped stage inherits.
- **Default tile `BK = 8`** (was 16). On the skeleton the difference is 2x: 64/64/16 at 152 byte-GMAC/s, 64/64/8 at 323, 4 x 8 register tiles at 97. In the prover: `lde` 10 to 5 ms, `quotient` 37 to 17 ms at 288 x 128; warm prove 326 to 305 ms. `LANE_TILE` (M = 8 lanes) is unchanged.
